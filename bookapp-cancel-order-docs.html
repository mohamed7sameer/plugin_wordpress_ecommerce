نظرة عامة

العميل يقدر يلغي طلب الدفع عند الاستلام من الأب طالما الأدمن لسه ما غيّرش حالته في الداشبورد. القواعد على السيرفر. الأب يعرض الزرار وينادي الـ endpoint بس.

  • الإلغاء من bookapp/v1 — مش من Store API ومش من wc/v3.
  • لازم مستخدم مسجّل (JWT). الزائر مفيش عنده قائمة طلبات وبالتالي مفيش إلغاء.
  • بعد النجاح الحالة تبقى cancelled والمخزون يرجع في ووكومرس تلقائيًا.
  • الطلبات الجاهزة للتجربة في bookapp-api.http (قسم ORDERS).
المسار الصح: POST /bookapp/v1/orders/cancel + order_id في البودي — نفس شكل التتبع. متستخدمش POST /orders/{id}/cancel. المسار المتداخل الـ CDN بيصده (403 Forbidden).

متى ينفع الإلغاء

السيرفر بيسمح بالإلغاء لو الشروط الثلاثة اتحققت معًا. الأب مايحسبش الشرط بنفسه.

الشرطالقيمةملاحظة
المالكالطلب بتاع نفس مستخدم الـ JWTطلب حد تاني → 404 مش 403
الدفعpayment_method === "cod"EasyKash والمدفوع أونلاين مش بيتلغوا من الأب
الحالةprocessing أو pendingيعني الأدمن لسه ما غيّرش الحالة (شحن / مكتمل / ملغي…)
أوردر COD على كتب ورقية عادة بيتعمل على طول بحالة processing (قيد التنفيذ). لو الأدمن غيّر الحالة، can_cancel يبقى false ولو الأب نادى الإلغاء يرجع 409.

فلاج can_cancel

الفلاج موجود في قائمة الطلبات، تفاصيل الطلب، وتتبع الطلب، ورد الإلغاء نفسه.

القيمةمعنى للأب
trueاعرض زر «إلغاء الطلب». المستخدم الحالي يقدر يلغي الطلب ده دلوقتي.
falseخبّي الزرار. مش COD، أو الحالة اتغيّرت، أو الطلب مش بتاع المستخدم الحالي (زي التتبع العام).
اعرض الزرار من can_cancel === true فقط. لو غيّرنا القاعدة بعدين (حالة جديدة مثلًا) الأب مش هيحتاج تحديث.
متعملش: status === "processing" && payment_method === "cod" على الجهاز. السيرفر هو المصدر الوحيد.

الأخطاء

شكل الخطأ ثابت في كل BookApp API: code + message + data.status.

{
  "code": "bookapp_auth_required",
  "message": "Login required.",
  "data": { "status": 401 }
}
HTTPcodeمتىعمل الأب
400 bookapp_missing_fields البودي من غير order_id متحصلش لو بتبعت الـ id من شاشة الطلب
401 bookapp_auth_required من غير JWT أو التوكن منتهي ارجع لشاشة الدخول
404 bookapp_order_missing الطلب مش موجود أو مش بتاع المستخدم رسالة «الطلب غير موجود» وارجع للقائمة
409 bookapp_order_not_cancellable مش COD، أو الحالة اتغيّرت، أو اتلغى قبل كده خبّي الزرار وحدّث الطلب من GET /orders/{id}
500 bookapp_order_cancel_failed ووكومرس فشل يغيّر الحالة رسالة عامة وجرب تاني

Response 400

{ "code": "bookapp_missing_fields", "message": "order_id is required.", "data": { "status": 400 } }

Response 401

{ "code": "bookapp_auth_required", "message": "Login required.", "data": { "status": 401 } }

Response 404

{ "code": "bookapp_order_missing", "message": "Order not found.", "data": { "status": 404 } }

Response 409 — مثال: EasyKash أو الأدمن غيّر الحالة

{
  "code": "bookapp_order_not_cancellable",
  "message": "This order cannot be cancelled.",
  "data": {
    "status": 409,
    "can_cancel": false,
    "order_status": "processing",
    "payment_method": "easykash"
  }
}
في خطأ 409: data.status = كود HTTP (409). حالة الطلب في data.order_status مش في status.

شغل الأب خطوة بخطوة

  1. سجّل دخول → خزن JWT.
  2. GET /orders ارسم القائمة. لو can_cancel === true ممكن تظهر شارة أو زر مختصر على الكارت.
  3. شاشة التفاصيل: GET /orders/{id}. زر «إلغاء الطلب» ظاهر فقط لو can_cancel === true.
  4. تأكيد من المستخدم (ديالوج).
  5. POST /orders/cancel بالجسم { "order_id": id }.
  6. نجاح 200: استبدل بيانات الشاشة بالرد. الزرار يختفي، الحالة «ملغي».
  7. 409: حدّث الطلب بـ GET وخبّي الزرار. الأدمن غالبًا غيّر الحالة.
  8. 401: توكن منتهي → إعادة تسجيل.
